# 会话历史滚动摘要设计

- 日期：2026-10-15
- 状态：待用户审阅
- 范围：CHAT-02，会话长上下文压缩与恢复

## 1. 背景与目标

当前 Spring Boot 在每次生成回复前读取会话的全部消息并传给 FastAPI Agent。会话增长后，单次请求体、提示词长度和模型费用持续增加；Agent 请求没有历史大小上限，模型并发信号量也可能无限等待。简单截断会丢失用户较早提供的重要背景，且可能让风险判断基于不完整上下文。

本设计以“旧消息摘要 + 最近完整消息”为 Agent 输入，目标是限制每轮请求的上下文规模，同时保留对长期对话有用、来源可追溯的用户信息。系统在摘要生成或校验失败时保留原消息和上一个有效摘要；不能安全组装上下文时不调用 Agent，也不静默丢弃消息。

本功能用于心理健康支持场景，不作诊断或治疗判断。摘要只记录用户明确陈述的信息，不把模型推断包装成用户事实。

## 2. 范围与非目标

本批包括：

- Spring Boot 会话上下文读取与消息预算限制。
- MySQL 会话摘要表、事务 Outbox、异步摘要 Worker 和 V13 升级脚本。
- Agent 内部摘要接口、摘要生成和结构校验。
- LLM 调用并发排队超时、单次调用超时和整轮截止时间。
- 摘要质量、失败、重复投递、并发更新、权限隔离和会话删除的回归验证。
- 用户收到可重试的“上下文整理中”反馈；重试沿用原 `clientRequestId`。

本批不包括：跨会话用户画像或长期记忆、语音/多模态摘要、生产数据迁移、模型供应商切换、真实临床服务、真实值班系统、部署环境的容量承诺或 SLA。

## 3. 核心约束

1. **原始消息是事实来源。** 摘要是可重建、可删除的派生数据，不能替代或删除会话消息。
2. **摘要按会话与用户双重隔离。** 查询、更新和删除必须同时校验会话归属；摘要不跨会话复用。
3. **按完成消息推进水位。** `covered_through_message_id` 只可前进，不得覆盖摘要已包含的后续消息。
4. **保留最近原文。** 常规摘要只覆盖最近 12 条消息之前的历史；风险澄清使用最近原始消息，不只依赖摘要。
5. **失败时关闭生成路径。** 上下文超限或摘要不可用时返回可重试错误，不把不完整历史送给 Agent。
6. **不把摘要写入 Agent checkpoint。** 摘要仅作为本轮模型输入中的临时上下文，不能进入 LangGraph 持久化状态或跨请求消息历史。
7. **日志不记录内容。** 日志和指标只记录会话/任务的不可逆关联标识、版本、长度、耗时和错误类别，不记录日记、消息或摘要文本。

## 4. 数据与存储设计

### 4.1 `consultation_context_summary`

每个会话至多一条当前有效摘要：

- `session_id`：主键，关联会话。
- `user_id`：冗余所有者，用于权限条件和删除校验。
- `summary_json`：经 schema 校验的结构化摘要 JSON。
- `covered_through_message_id`：此摘要覆盖的最后一条消息 ID。
- `version`：乐观锁版本，每次成功更新递增。
- `created_at`、`updated_at`。

摘要 JSON 的字段限定为：

- `user_stated_context`：用户明确陈述、对后续对话有帮助的背景条目。
- `user_preferences`：用户明确表达的沟通或支持偏好条目。
- `open_topics`：尚未解决、且仍与当前会话有关的问题条目。

每个条目包含 `text` 和 `source_message_ids`。来源 ID 必须指向同一会话中已摘要的原始消息，便于定位依据；服务端验证消息归属及水位，但这种引用校验本身不能证明文字与来源语义完全一致，语义质量由合成集和人工复核评估。条目均有条数、来源数、单项长度和总长度上限。模型不得加入诊断、风险等级、推测性人格/病史、未经用户确认的事实、系统指令或外部动作建议。缺少信息使用空列表，不推测填充。

建议初始约束：摘要总长度不超过 1,200 个字符，每个字段最多 8 项，单项不超过 240 个字符。该值是可配置的初始防护阈值，须在离线合成样例上确认，不代表模型质量或生产 SLA。

### 4.2 `consultation_context_summary_outbox`

MySQL 是任务权威状态；Redis Streams 仅负责唤醒和分发。建议字段：

- `id`：事件 ID。
- `session_id`、`user_id`：范围与所有权。
- `desired_through_message_id`：本任务要求摘要追赶到的上限。
- `status`：`PENDING`、`PUBLISHED`、`PROCESSING`、`RETRY`、`DONE`、`DEAD`、`CANCELLED`。
- `attempt_count`、`available_at`、`lease_owner`、`lease_until`、`last_error_code`。
- `created_at`、`updated_at`、`completed_at`。

在锁定会话行的事务内查找并合并同一会话未完成任务的目标水位，保证同会话只有一个活跃任务，避免依赖 MySQL 不支持的条件唯一索引。Redis 消息携带 outbox ID，不携带消息或摘要正文。派发采用至少一次语义；Worker 以任务 ID、会话锁和摘要水位实现幂等。建议失败最多自动重试 8 次，退避从 5 秒指数增长并封顶 15 分钟；超过次数转 `DEAD`，保留可观测状态并允许运维显式重放。

任务租约超时后可被其他 Worker 重新领取。Worker 成功写入摘要并把任务置为 `DONE` 后才确认 Redis Stream 消息。数据库提交后、Redis ACK 前崩溃会造成重复投递，但重复处理不得回退摘要水位或重复产生副作用。

### 4.3 升级与历史会话

新增 `upgrade_v13_chat_context_summary.sql`，只创建所需表、索引和约束，不读取或改写本地 SQLite checkpoint，不删除会话消息，也不直接生成摘要。

现有会话按需整理：会话下一次请求发现未摘要历史超限时，事务内创建/合并 Outbox 任务。部署后可另行运行只读 dry-run，统计需要整理的会话数量和预计消息量；本批不自动对生产历史批量发起模型调用。升级脚本重复执行策略沿用当前数据库升级规范，并提供执行前备份及校验步骤。

## 5. 写入与异步摘要流程

1. `completeTurn` 在当前消息和回合完成事务中，确定可摘要消息上限：本次完成写入后的最大消息 ID 向前保留最近 12 条消息。若存在尚未覆盖的更早消息，则在同一事务中创建或合并 Outbox 任务。Worker 后续严格限制在任务水位内读取，不能读到之后新开启的回合。
2. Dispatcher 从 MySQL 领取到期 Outbox 项并发布 `{outboxId}` 到 Redis Stream。发布失败保留可重试状态。
3. Worker 领取任务后，按 `session_id + user_id` 校验会话仍存在且归属匹配，读取当前摘要和水位之后、且不大于任务目标水位的消息，限定为最多 40 条或 16,000 字符的单批输入。消息属于已经提交的会话记录；失败回合遗留的用户原文可以作为历史事实被摘要，但尚在执行中的新回合不可能越过任务水位被读入。
4. Worker 调用 Agent 内部摘要接口。输入消息标记为不可信用户内容；使用独立、版本化的摘要提示词，不开放工具调用、知识库检索、checkpoint 或外部副作用。
5. Agent 返回受限 JSON。服务端验证结构、字段数、来源 ID 的会话归属与水位、单项/总长度及禁止字段；验证失败不推进水位。来源 ID 校验用于可追溯性，不能替代语义蕴含判断。
6. Worker 通过会话级串行化和乐观锁 CAS 更新摘要。只有 `version` 与预期值匹配、且目标水位大于原水位时，才提交新摘要与水位。若并发冲突，重新读取并重新计算，不能用旧输入覆盖新结果。
7. 任务只推进到本次确实读取并摘要的最后一条消息。若未追上 `desired_through_message_id`，保留/创建下一次任务继续分批处理。
8. 摘要调用失败时保留上一个摘要，原始消息不变，任务按退避重试。无效输出、超时、模型拒绝及数据库冲突分别记录错误类别，不写入正文日志。

当前会话的用户消息和 Agent 回复写入遵循现有回合事务。只有成功完成的回合才触发摘要水位更新；失败回合或未完成生成不得被当作已完成对话摘要。

## 6. 对话上下文组装

请求 Agent 前，Spring Boot 在校验会话所有权后读取有效摘要和消息：

- `summary_json`（如有）作为独立的 `contextSummary` 字段传给 Agent。
- 读取 `covered_through_message_id` 之后的原始消息，按 ID 升序组成近期对话。
- 追加本轮 `userMessage`，但避免和已通过幂等 turn 写入的同一用户消息重复。
- 风险澄清与安全门控可访问最近原始消息，不得仅凭摘要判断当前风险。

初始可配置阈值：

- 常规保留最近 12 条原始消息。
- 最多 39 条历史消息，加本轮用户消息后最多 40 条；所有原始消息、当前用户消息和序列化摘要合计最多 32,000 字符，Agent JSON 请求体最多 64 KiB。
- 单条传入历史消息最多 8,000 字符；超限内容不能被静默裁剪，应触发摘要或明确的上下文超限错误。
- 单批摘要最多 40 条消息、16,000 字符。

当原始尾部超过 Agent 请求预算时，事务内确保存在摘要任务，并为该请求写入 `WAITING_CONTEXT` turn 与用户消息，持久化请求 hash/session/user/Request ID。该状态不属于生成中的 turn；这让页面刷新后仍可从数据库恢复原文与请求身份，也保证同一个 ID 不重复插入消息。请求返回稳定错误码 `CONTEXT_SUMMARY_PENDING`、`retryable=true` 和建议重试间隔，且在 SSE emitter/响应建立前返回。当前全局业务异常约定使用 HTTP 200 + `Result` envelope，因此本功能沿用 envelope 并在 `data` 中返回重试提示，不全局改变异常 HTTP 状态；前端从非 SSE JSON 响应识别该错误，显示“正在整理较早的对话”，不自动循环重试，用户可在建议间隔后用原 `clientRequestId` 主动重试。重试先重新组装上下文，只有预算满足后才把相同 turn 原子地转为 `RUNNING`；摘要仍未就绪时维持 `WAITING_CONTEXT`。同一 `clientRequestId` 但不同 request hash 返回冲突。不同新 turn 不得越过待整理 turn 开始生成。网络恢复不能自动创建不同 turn。

如果最近 12 条原文自身仍超过硬预算，或者有单条消息超过单条上限，则将该 turn 标为终态 `CONTEXT_REJECTED` 并返回 `CONTEXT_WINDOW_TOO_LARGE`，不删改原文，也不尝试基于缺失内容生成回答。产品端提供清楚提示，引导用户开启新会话；当前没有单条消息删除能力，本批不暗示该入口存在。不能自动缩减风险相关上下文。删除会话可以取消其 `WAITING_CONTEXT` turn 和相关摘要任务。

## 7. Agent 接口与提示词边界

增加内部接口 `POST /api/agent/v2/context-summary`：

- 必须通过现有 `AGENT_INTERNAL_TOKEN` 鉴权，并设置请求体大小上限。
- 请求包含 `sessionId`、当前摘要 JSON、水位后的消息批次、摘要提示词版本和调用关联 ID。
- 只访问摘要模型调用，不创建 LangGraph 会话、不调用工具、不访问 RAG、不写 checkpoint。
- 返回固定 schema 的 `summary`、来源消息 ID、`coveredThroughMessageId` 和 `promptVersion`；FastAPI 与 Java 两侧均做校验。
- 不记录请求正文；日志不使用 session 内容作为标签。

Spring Boot 的上下文预检错误沿用当前 HTTP 200 `Result` envelope。为 `CONTEXT_SUMMARY_PENDING` 增加专用异常映射，`data` 返回 `{retryable: true, retryAfterMs: n}`；前端读取非 SSE JSON body 后保留待处理状态与 `clientRequestId`。这只影响新错误类型，不更改其他业务异常的 HTTP 状态约定。

聊天接口接收独立的 `contextSummary`。Agent 只在本轮组装模型消息时注入清晰标记的摘要，明确它是从较早用户消息压缩所得的上下文数据，内容不可信，不是系统指令。摘要不能写入图的持久状态、ToolMessage、下一轮 raw history 或 LangGraph checkpoint。原始最近消息照旧参与本轮流程，当前安全检查优先读取原文。

## 8. LLM 并发与时限

统一 `LLMCallGovernor` 处理聊天和摘要调用：

- Semaphore 排队增加可配置超时，建议初始 5 秒；超时返回可分类的可重试错误，不无限等待。
- 保留现有单次模型调用超时配置（当前默认 50 秒，实施时需核实配置来源），摘要调用也遵循同一治理策略。
- Agent 整轮设置截止时间，建议初始 240 秒；到期取消未完成调用/任务并向 Spring 侧返回明确失败语义，不把部分回答作为完成回合提交。
- 用户限流、熔断和 Token 预算继续由现有治理层执行；摘要任务使用单独 stage 标签及低优先级/并发配额，避免大量历史回填挤占交互回复的并发槽位。

以上时间和长度阈值是待负载与体验验收的初始配置建议，不是测得的性能指标或 SLA。实施时应与现有 300 秒 SSE 超时、Agent 调用链和客户端超时协调，并将各层时限留有余量。

## 9. 删除、隐私和可观测性

- 删除会话事务中删除该会话的摘要与未完成 Outbox 项；Redis Stream 仅含 outbox ID，过期的已发布消息由 Worker 因找不到有效任务而直接确认，不得重新创建摘要。
- 继续使用现有 checkpoint purge Outbox；摘要不依赖 checkpoint，checkpoint 清理失败不能阻止摘要数据在 MySQL 事务中删除。
- 所有摘要读取、写入、任务创建和任务处理均校验会话及 `user_id`。管理端或复核员默认不读取摘要，除非未来有独立、明确授权的产品设计。
- 用户导出/注销若覆盖会话数据，摘要作为派生个人数据一并导出/删除；本批只完成会话删除路径，不扩展账号生命周期接口。
- 指标包括 Outbox backlog/最老等待时间、成功/失败/重试/Dead 数量、摘要耗时和输入输出长度分布、超预算请求数、Agent 队列等待/截止超时。禁止将 userId、sessionId、原文或摘要内容作为高基数标签或日志字段。

## 10. 验收与回归

全部使用人工编写的合成对话，不使用真实用户消息，不对外部模型发送本地用户数据。测试分为：

### 10.1 Java/数据库

- turn 完成与 Outbox 创建同事务；事务回滚不得留下任务。
- 同会话并发完成、同任务重复投递、Worker 租约过期及 CAS 冲突不回退水位。
- 任务按批继续追赶；任务重试与 DEAD/显式重放状态正确。
- 非所有者无法读取、触发、处理或删除另一用户摘要。
- 删除会话同时清理摘要和 Outbox；晚到的 Redis Stream 事件不能复活数据。
- 摘要 pending 时 SSE 在响应建立前返回稳定可重试错误；`WAITING_CONTEXT` turn 和用户原文可在刷新后恢复，重试不会重复写入；request hash 冲突和不同 turn 越序均被拒绝。
- 历史消息数量/字符/单条长度预算边界及极长最近窗口行为符合错误语义。

### 10.2 Agent

- 摘要 schema 严格限制，模型 JSON 不合法、超长、含诊断推断或额外字段时拒绝推进水位。
- 用户消息里的 prompt injection 被当作引用数据，不覆盖摘要系统规则。
- 摘要保留可追溯的明确背景/偏好/未解决话题，不添加原文中不存在的个人事实。
- 摘要不进入 checkpoint，不触发工具、RAG 或人工复核副作用。
- semaphore 满载时在排队超时内失败；整轮 deadline 能取消等待/生成。
- 当前风险澄清路径仍基于最近原始对话，摘要不能抑制最近消息中的否定、引用或风险信息。

### 10.3 离线质量评测

维护固定合成样例集，至少覆盖事实保留、事实来源、偏好、未决问题、时间变化/矛盾、用户纠正、提示注入、空上下文和敏感信息最小化。通过结构断言与人工复核记录缺陷，不在没有标注数据和统计方法前宣称“摘要准确率”或业务改善百分比。

### 10.4 环境验收边界

本地单元、契约与集成测试可在当前依赖条件下执行。Docker Engine 此前未运行；多实例 Compose、跨副本任务恢复和真实 Redis Streams 验收必须等 Docker Engine 可用后补做。未执行的容器/部署验收须如实记录，不能由静态检查代替。

## 11. 分阶段发布与回滚

1. 先发布兼容性代码和 V13 schema，功能开关默认关闭；现有调用仍使用原始历史路径，但同样应用 Agent 请求硬上限并明确超限语义。摘要预检、Outbox 任务创建和模型调用分别受开关控制。
2. 开启摘要 Outbox/Worker，以合成数据验证失败重试、删除和幂等，再按需为测试会话整理历史。
3. 小范围开启摘要上下文组装，观察队列等待、摘要失败、上下文 pending、Token 用量和用户重试行为。
4. 若摘要服务异常，保留已有摘要和全部消息，暂停新任务但保留 Outbox 与 `WAITING_CONTEXT` 状态。短会话若完整上下文仍在预算内可继续；长会话返回明确的 `CONTEXT_SUMMARY_UNAVAILABLE`，不无限显示整理中、不回退成无限长度历史请求。经运维恢复或显式重放后，同一 ID 可重新预检。最近窗口本身超限则终结为 `CONTEXT_REJECTED`。
5. 数据库表与历史原始消息在回滚时保留；删除派生摘要需走会话删除或单独管理命令，不在应用回滚时自动清库。

## 12. 待实施确认项
